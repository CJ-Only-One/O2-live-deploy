# O2-live-deploy

**Argo CD가 감시하는 저장소.** 여기 있는 매니페스트가 곧 클러스터의 현재 상태다.

## 사람이 직접 고치지 말 것

이미지 태그는 [`O2-live-ai-ops`](https://github.com/CJ-Only-One/O2-live-ai-ops)의
`app.yml` 워크플로가 자동으로 갱신한다. 손으로 고치면 다음 배포에서 덮어써진다.

애플리케이션을 배포하려면 **앱 저장소에 코드를 머지**하면 된다.
그러면 이미지가 빌드되어 ECR에 올라가고, 그 결과가 이 저장소에 커밋된다.

```
O2-live-ai-ops 에 머지
  → 이미지 빌드 → ECR
      → 이 저장소의 api-deployment.yaml 태그 갱신    ← 봇이 한다
          → Argo CD가 감지(최대 180초) → EKS 반영
```

## 왜 저장소를 나눴나

앱 저장소는 `main` 에 브랜치 보호가 걸려 있어 PR 없이는 푸시할 수 없다.
그런데 CI가 배포할 때마다 태그 갱신 커밋을 밀어야 해서 규칙과 충돌했다.

우회 권한을 주는 방법도 있었지만, 그러면 앱 저장소 히스토리에 봇 커밋이
사람 커밋만큼 쌓인다. 코드의 생명주기와 배포 기록의 생명주기는 다르므로
저장소를 나눴다. 이 저장소의 커밋은 **로그에 가깝고**, 리뷰 대상이 아니다.

배경은 앱 저장소의 `docs/decisions.md` 를 참고할 것.

## 무엇이 들어 있나

| 파일 | 내용 |
|---|---|
| `00-namespace.yaml` | `o2-dev` 네임스페이스 |
| `api-deployment.yaml` | api 서비스. **이미지 태그만 CI가 고친다** |
| `api-service.yaml` | api 서비스의 ClusterIP |
| `.github/workflows/validate.yml` | `kubeconform -strict` 로 매니페스트 검사 |

파일명은 `<service>-deployment.yaml` 규약을 따른다.
CI가 `yq` 로 이 경로를 찾아 태그를 고치기 때문이며,
이름이 어긋나면 갱신이 조용히 건너뛰어진다.

## 사람이 손대야 하는 경우

레플리카 수, 리소스 요청량, 환경변수, probe 설정 같은 것은 여기서 직접 고친다.
이미지 태그를 제외한 나머지는 전부 사람의 몫이다.

고치면 `validate` 워크플로가 `kubeconform -strict` 로 검사한다.
`-strict` 는 스키마에 없는 필드를 오류로 본다 — 오타 난 필드는 조용히 무시되어
"적용은 됐는데 설정이 안 먹는" 상태를 만들기 때문이다.

수정하면 Argo가 180초 안에 반영한다. 되돌리려면 `git revert` 하면 된다 —
이전 이미지로 롤백하는 방법도 같다.

## 접근 권한

CI는 **fine-grained PAT**(`DEPLOY_REPO_TOKEN`)으로 이 저장소에만 푸시한다.
범위는 이 저장소 하나, `Contents: Read and write` 뿐이라 유출되어도 피해가 여기로 한정된다.
deploy key를 쓰려 했으나 org 설정에서 비활성화되어 있었다(앱 저장소 D-006).

**토큰에 만료가 있다.** 만료되면 배포가 인증 오류로 멈춘다.
